# 物流产品与出库链路审计报告

审计日期：2026-08-24  
审计范围：ERP 货主端订单确认、物流产品选择、海外仓订单下架、拣货任务、逐单/整单作业、打包签出，以及旧销售出库链路残留。  
本轮仅审计代码和当前数据库，没有修改业务代码或数据。

## 一、结论摘要

新版主链路已经建立，平台订单确认后会直接创建 `wms_fulfillment_order`，不再需要先创建销售出库单。海外仓后续的订单下架、拣货、面单、打包和签出也都以履约订单为核心。

但是，“去掉销售出库单”目前只完成了新链路建设，没有完成旧链路退场。旧菜单、旧接口、旧表和旧订单字段仍在使用范围内，而且新旧链路之间没有互斥校验。当前还不能认为销售出库单已经完整移除。

当前发现 3 个需要优先修复的问题和 2 个数据/展示问题。

## 二、货主在哪里选择物流产品

货主有两个选择位置。

### 1. 店铺默认物流产品

菜单路径：`系统管理/店铺管理`，新增或编辑店铺时设置：

- 默认 WMS 仓库
- 默认物流产品

前端位置：`erp-frontend/src/views/shop/ShopFormModal.vue` 第 75-89 行。保存时两个字段都是必填，第 264-267、475-483 行会提交到店铺配置。

作用：订单确认时如果不临时指定物流产品，后端自动使用订单所属店铺的默认物流产品。

### 2. 订单确认发货弹窗

菜单路径：各平台订单管理，例如 Ozon、WB、Yandex 订单页面，点击“确认发货”后在弹窗中选择物流产品。

前端位置：

- `erp-frontend/src/views/order/components/OrderConfirmModal.vue` 第 15-21 行
- `erp-frontend/src/views/order/hooks/useOrderConfirm.ts` 第 56-67 行

规则：

- 留空：每个订单使用其店铺的默认物流产品。
- 手工选择：本次所选订单统一使用该物流产品，覆盖店铺默认值。
- 可选范围：只显示当前货主所属 WMS 服务商已启用的产品。

后端在 `ErpOrderFulfillmentSubmissionService.java` 第 60-64 行再次校验产品是否启用、是否属于当前货主绑定的 WMS 服务商，因此不能越权选择其他服务商的产品。

货主没有“物流产品管理”菜单，这是正确的。物流产品由 WMS 服务商维护，货主只有选择权。

## 三、当前新版出库流程

```text
ERP 平台订单
  -> 货主点击确认发货
  -> 选择本次物流产品，或使用店铺默认产品
  -> 校验 FBS、仓库、货主、服务商、SKU 尺寸重量和库存
  -> 创建一单一包裹的 wms_fulfillment_order
  -> 立即预占库位库存
  -> ERP 内部仓库状态变为 WAITING_SHELF（待下架）
  -> 海外仓“订单下架”按仓库批量确认
  -> 调用对应平台动作，并把订单推进到 WAITING_PICK
  -> 按仓库自动生成拣货任务
  -> 仓库员工领取任务
  -> 逐单扫描取货，或使用整单简化作业
  -> 获取并打印平台面单
  -> 核验面单、记录承运商/运输方式/跟踪号/重量
  -> 完成打包，状态变为 PACKED
  -> 单个或批量签出
  -> 扣减已预占库存，记录仓储出库费和物流产品费
  -> 状态变为 SHIPPED，并同步 ERP 订单内部仓库状态
```

平台动作时点当前为：

- Ozon：订单下架时确认平台订单；面单阶段取平台面单；签出为本地完成记录。
- WB：订单下架时执行 prepare；签出时执行 finalize。
- Yandex：订单下架先在仓库接单；面单核验时调用平台确认。

三者时点不同是平台 API 生命周期差异，不是所有平台都必须在同一步调用同名接口。

## 四、问题清单

### P1：旧销售出库和新版履约可以同时作用于同一平台订单

证据：

- 新链路提交只检查 FBS、仓库、物流产品和库存，没有检查旧字段 `outbound_status/outbound_order_id`：`ErpOrderFulfillmentSubmissionService.java` 第 43-66 行。
- 旧销售出库待选订单只检查 `outbound_status='NONE'`，没有排除已有 `fulfillment_order_id` 的订单：`ErpOrderMapper.xml` 第 283-304 行。
- 当前数据库中“销售出库单”菜单仍可见，并授权给 JHIN 的管理员和经理角色。
- 前端旧表单路由和后端 `/wms/sales-outbound` 全套接口仍然存在。

影响：同一订单可能先进入新版履约，再被旧销售出库选择；也可能先关联旧销售出库，再提交新版履约。最终会造成重复预占、创建失败、状态冲突或两个页面对同一订单给出不同结论。

建议：

1. 从 ERP 货主角色菜单中移除“销售出库单”，保留“人工出库”。
2. 旧待选订单 SQL 增加 `fulfillment_order_id IS NULL` 和 `outbound_order_id IS NULL`。
3. 新履约提交增加旧链路互斥校验：`outbound_order_id IS NULL` 且 `outbound_status='NONE'`。
4. 旧控制器暂时保留只读兼容或直接停用新增、确认入口，待历史数据迁移完成后再删除代码和表。

### P1：现有店铺没有默认 WMS 仓库，真实订单无法提交新版履约

当前数据库：

- 4 个店铺都有默认物流产品 `2`。
- 4 个店铺的 `default_wms_warehouse_id` 全部为空。
- 当前 6887 条平台订单中，尚无一条关联新版履约单；现有 6 条履约记录全部是人工测试单。

前端确认弹窗只允许选择物流产品，没有仓库选择控件；调用时 `wmsWarehouseId` 固定传 `undefined`。后端只能回退到店铺默认仓库，见 `useOrderConfirm.ts` 第 64-67 行和 `ErpOrderFulfillmentSubmissionService.java` 第 49-53 行。

影响：当前真实平台 FBS 订单点击确认时会提示先配置默认 WMS 仓库，无法进入订单下架。

建议：先为每个启用店铺补齐默认 WMS 仓库。为避免以后再次出现，店铺列表增加“默认仓库/默认物流产品是否完整”的醒目标识；确认弹窗可选增加临时仓库覆盖，但这不是必须项。

### P1：下架成功与自动创建拣货任务不是一个原子业务动作

`FulfillmentDispatchService.java` 第 24-57 行先逐单调用平台并把状态推进为 `WAITING_PICK`，然后才按仓库创建拣货任务。整个 `dispatch()` 没有统一事务；即使增加数据库事务，也无法回滚已经成功的平台调用。

如果下架成功后创建任务失败：

- 订单已经不是 `WAITING_SHELF`，订单下架页复选框会置灰。
- 页面只显示“已下架但派单失败”。
- 拣货任务页面没有为这些游离订单提供重新派单入口。

影响：普通数据库异常、预占数据异常或任务插入异常都可能让订单停在 `WAITING_PICK`，但没有拣货任务可领取。

建议：

1. 增加“待派单/派单失败”恢复入口，按仓库重新生成任务。
2. 下架动作成功后即使自动派单失败，也必须保存明确的派单状态和失败原因。
3. 增加定时补偿或人工“重新派单”按钮，不能要求再次调用平台下架接口。

### P2：平台订单履约快照没有写入收件人信息

`ErpOrderFulfillmentSubmissionService.buildCommand()` 第 89-127 行写入了仓库、店铺、物流产品、来源订单和商品，但没有设置 `recipientName/recipientPhone/recipientAddress`。`FulfillmentOrderService.buildOrder()` 第 107-109 行虽然支持这些字段，实际收到的值为空。

影响：订单下架和出库作业页面的“收件人”列对平台订单会显示为空，历史履约快照也缺少收件信息。平台面单仍按来源订单调用平台接口，不一定因此打印失败，但仓库人工核对信息不完整。

建议：从各平台订单标准字段或 `raw_json` 中统一提取可获得的收件信息并写入履约快照；平台因隐私规则不提供时明确显示“平台未提供”，不要与程序漏写混在一起。

### P2：数据库残留 42 条失效的旧销售出库关联

当前数据库中：

- `wms_sales_outbound_order` 已无业务记录。
- 仍有 42 条 `erp_order.outbound_order_id` 指向不存在的旧销售出库单。
- 这 42 条订单的 `outbound_status` 又都是 `NONE`。

影响：旧页面可能把这些订单显示为可选，但绑定旧销售出库时会因已有 `outbound_order_id` 而失败；同时也会干扰后续新旧链路互斥判断。

建议：确认旧销售出库业务已经废弃后，将这 42 条孤儿引用的 `outbound_order_id` 清空，并在迁移脚本中加入数据修复和约束检查。

## 五、正常部分

- 新履约使用 `(source_type, source_order_id, deleted)` 唯一约束，正常并发下不会为同一来源订单创建两张履约单。
- 订单提交时立即预占库位库存，货主在下架前可以取消并释放预占。
- 一张履约单对应一个平台订单/物理包裹，符合当前约定。
- 下架批量处理会按仓库拆分拣货任务，不按货主拆分，符合已确认规则。
- 拣货任务保留逐单扫描和整单简化作业两种模式，并互相限制，避免同一任务混用。
- 面单获取、面单核验、打包、签出均校验当前任务操作员。
- 只有 `PACKED` 订单可以签出；批量签出逐单返回成功和失败结果。
- 签出时扣减预占库存，并分别记录海外仓出库服务费与 WMS 服务商物流产品费。
- ERP 订单的 `warehouse_fulfillment_status` 会随下架、拣货、打包、签出同步；平台业务状态仍由后续平台同步任务更新。
- 人工出库已经使用新版 `wms_fulfillment_order`，且一张人工单就是一个包裹，不需要恢复旧自定义出库流程。

## 六、建议实施顺序

1. 先补齐 4 个店铺的默认 WMS 仓库，恢复真实订单可提交能力。
2. 隐藏旧“销售出库单”菜单，并同时在新旧后端增加互斥校验。
3. 清理 42 条孤儿 `outbound_order_id`。
4. 增加 `WAITING_PICK` 无任务订单的重新派单能力。
5. 补齐平台订单履约快照中的收件信息。
6. 用 Ozon、WB、Yandex 各一条真实 FBS 订单完成端到端回归：确认发货、下架、领取任务、取货、打印面单、打包、签出、费用和状态同步。

## 七、最终判断

新版出库主流程的方向正确，已经能够绕过销售出库单直接执行订单级仓库履约；但旧销售出库尚未真正退出系统，而且当前店铺仓库配置为空，所以生产使用前仍需完成上述 P1 修复。完成后，货主端应只保留“平台订单确认发货”和“人工出库”两个入口，海外仓统一处理订单下架、拣货和出库作业。
