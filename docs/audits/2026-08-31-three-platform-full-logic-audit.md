## 二、确认问题

### P1：活动库位管理页仍保留旧几何库位、托盘和托位内核

当前系统已经采用逻辑库位库存，上架、移库、盘点、报废和出库履约均应直接操作库位库存。审计时发现仓库中仍保留一份旧抽屉代码，虽然已不再被活动页面引用，但仍包含：

- 排数、每排列数、层数、每层托位；
- “保存并生成”旧二维库位结构；
- 托盘规则、托位标签和托盘层位接口；
- `location_generated` 旧生成状态。

证据：

- `erp-frontend/src/views/wms/location-mgmt/WarehouseLocationDrawer.vue`（修复后已删除）。
- `erp-backend/admin/src/main/java/com/erp/admin/wms/controller/WmsLocationManageController.java` 第 118、125 行仍暴露旧结构生成和托盘规则写接口。
- `erp-backend/admin/src/main/java/com/erp/admin/wms/service/WmsLocationGenerator.java` 第 119 行仍按旧结构删除并重建库位。

当前数据库仓库 `CK1 / 李安` 已有 2 个逻辑库位和 24 件库存，但 `wms_warehouse.location_generated=0`。列表通过实际库位数量显示“已配置”，抽屉内部却仍按旧标记判断“未生成”，形成同一仓库两套状态口径。

影响：

- 普通用户会误以为还需要生成托位、维护托盘规则和打印托位标签。
- 空仓新增逻辑库位后，旧“保存并生成”仍可能重建库位，与已经确认的“按排逐个维护逻辑库位”流程冲突。
- `location_generated` 与实际库位数量不一致，页面锁定状态和提示可能错误。

修复方案：

1. 从活动库位管理抽屉删除旧结构设计、托盘规则、托位预览和托位标签功能。
2. 页面只保留排管理、库位增删改、分区、长宽高、最大体积、最大承重和公共共享属性。
3. 后端将 `/structure`、`/pallet-rules` 以及旧托位查询接口在 `LOGICAL_LOCATION` 模式下统一停用。
4. 页面配置状态只以实际逻辑库位数量判断；不再读取 `location_generated`。
5. 保留旧表和历史代码一轮版本用于回溯，但从菜单、活动 API 和业务服务中完全断开。

### P2：14 个历史 SKU 缺少外箱尺寸或单箱毛重

当前数据库有 14 个历史 SKU 缺少新的必填外箱参数。当前有库存的 5 种 SKU 参数完整，因此库位利用率和现有拣货不受影响。

影响：历史 SKU 若再次用于入库、容量统计或上架，系统无法计算体积和承重，只能跳过容量计算或在相关页面提示参数不完整。

修复方案：增加一次 SKU 数据治理页面或导入模板，列出缺少 `outer_length_mm`、`outer_width_mm`、`outer_height_mm`、`outer_gross_weight_g` 的 SKU；补齐前禁止用于新入库单。现有 SKU 新建和编辑校验继续保留。

### P2：菜单数据库仍依赖前端组件覆盖并保留退休菜单元数据

`退货质检`、`仓储概览`等菜单的 `sys_menu.uri` 仍指向 `common/Placeholder`，由 `dynamic-routes.ts` 按 path 覆盖为真实页面；`自定义退货单`仍为活动菜单记录，但没有任何角色授权，并由前端再次隐藏。

当前运行不受影响，但菜单配置、前端覆盖和角色授权形成三套真相，后续改 path、做权限复制或部署不同前端版本时容易重新出现空白页或菜单丢失。

修复方案：新增菜单收敛迁移，将真实页面 URI、hidden 状态和角色权限直接写入 `sys_menu/sys_role_menu`；移除已经不需要的前端特殊覆盖和双重隐藏逻辑。
