## 三、确认的问题

### P1-1 新库存表与商品表排序规则不一致，库存接口会直接报错

`sku.sku_code` 使用 `utf8mb4_0900_ai_ci`，而 `wms_location_inventory.sku_code` 使用 `utf8mb4_unicode_ci`。

`OwnerInventoryQueryMapper.xml` 第 26、42 行按 SKU 编码连接这两张表。对当前真实数据库执行同等 SQL 已稳定复现：

```text
ERROR 1267: Illegal mix of collations ... for operation '='
```

影响范围：ERP 货主端的库存总览、库存明细，以及复用该查询的库存展示接口可能直接失败。

修复方案：新增 V138 迁移，把新库存内核和新履约表的字符集排序规则统一为项目现有的 `utf8mb4_0900_ai_ci`；迁移后执行真实连接查询，不使用只检查 SQL 文本的测试代替数据库验证。

### P1-2 货架分配仍用旧物理库存判断是否有货

`WmsRackAssignmentService.java` 第 91、137 行通过 `WmsPhysicalInventoryMapper` 检查排内库存。旧表当前为空，但新库存中已有 24 件。

影响范围：仓库管理 -> 货架分配。系统可能允许重新分配或解除仍存有货物的排，造成服务商归属与库存归属不一致。

修复方案：在 `WmsLocationInventoryMapper` 增加按仓库、排号汇总 `quantity`、`reserved_quantity` 和 `wms_tenant_id` 的查询，分配和解除分配统一使用新库存。

### P1-3 库位改分区与有货库位锁定仍读取旧库存

`WmsLocationManageController.java` 第 204-208 行的“已占用库位”接口仍调用旧物理库存服务；`WmsZoneService.java` 第 71 行也通过旧表判断目标库位是否为空。

影响范围：仓库管理 -> 库位管理。前端可能不再置灰有货库位，后端也可能允许把有货库位直接改到其他分区。

修复方案：占用口径改为新库存中 `quantity > 0 OR reserved_quantity > 0`；新库存不再冗余写入分区字段，分区直接由 `wms_location.zone_id` 关联获得。

### P1-4 仓库结构锁定仍读取旧库存

`WmsStructureLockService.java` 第 107 行通过旧表统计占用库位。当前新库存有货时，该服务仍可能返回未占用。

影响范围：库位结构保存、重新生成等操作。若其他锁定条件也不存在，可能错误放行破坏性结构操作。

修复方案：结构锁定改为查询 `wms_location_inventory`，并继续保留有效货架分配、未完成调整单、进行中盘点等附加锁定条件。

### P1-5 合同退款的“仓库无剩余货物”判断仍读取旧库存

`ServiceContractService.java` 第 199-214 行从 `wms_physical_inventory` 汇总库存和预留。旧表为空时，即使新库存有货，也会把 `noRemainingGoods` 判为 true。

影响范围：海外仓平台 -> 合同资金 -> 合同退款检查。可能错误允许仍有库存的服务商合同进入退款。

修复方案：按合同的服务商、仓库，从 `wms_location_inventory` 汇总 `quantity` 与 `reserved_quantity`，退款执行时仍在事务内重新校验。

### P2-1 WMS 服务商运营看板在库总量错误显示为 0

`OperatorDashboardMapper.xml` 第 114-120 行仍从 `wms_physical_inventory` 汇总。当前数据库中 WMS_FIRST 的新库存为 24 件，旧表为 0，因此该指标必然显示 0。

修复方案：改查 `wms_location_inventory`，按 `wms_tenant_id` 和货主范围过滤，并增加“新库存有值、旧库存为空”的回归测试。

### P2-2 旧库存与旧出库代码仍大量保留

旧销售出库菜单已隐藏，旧写接口也受 `LOGICAL_LOCATION` 模式保护，当前不会自动污染新库存；但旧物理上架、托盘、旧拣货和旧移库服务仍在代码中，增加了误调用风险。

修复方案：本轮先修仍被活动页面调用的代码；随后建立旧内核退休清单，将旧控制器统一返回 410、删除动态路由兼容入口，最后再删除无引用服务和 Mapper。不要在同一轮直接删表。

### P3-1 全仓 ESLint 目前不能作为发布闸门

全仓 ESLint 结果为 20 个错误、1391 个警告，多数来自既存组件命名和历史 Prettier 格式；但类型检查、功能测试和生产构建均通过。

修复方案：单独建立代码质量任务，先处理 20 个 error，再逐目录收敛 warning；不要与新数据库修复混在同一次提交中。

## 四、建议实施顺序

1. 备份数据库，并记录新旧库存及预留汇总基线。
2. 增加 V138 排序规则统一迁移，先解决库存接口直接报错。
3. 为新库存 Mapper 增加占用库位、排归属、仓库汇总和合同退款汇总查询。
4. 替换货架分配、库位分区、结构锁、合同退款、服务商看板中的旧表依赖。
5. 对仍暴露的旧库存写接口补齐模式禁用或 410 响应。
6. 增加真实 MySQL 集成测试，覆盖排序规则连接、占用锁定和退款拦截。
7. 使用 ERP 货主、WMS 服务商、海外仓平台三个身份逐页回归。
