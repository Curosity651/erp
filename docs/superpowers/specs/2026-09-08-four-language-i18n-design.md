# ERP 四语言国际化设计

## 1. 目标

为 ERP 货主端、WMS 服务商端和海外仓平台端提供统一的语言切换能力，支持：

- 简体中文：`zh-CN`，默认语言
- 英文：`en-US`
- 乌克兰语：`uk-UA`
- 俄语：`ru-RU`

国际化覆盖全部用户可见内容，包括网页、动态菜单、状态和枚举、校验与异常提示、打印单据、商品标签、Excel 导出文件及文件名。SKU、商品名称、货主名称、地址、备注等业务数据保持原始内容，不自动翻译。

## 2. 已确认规则

1. 首次访问使用简体中文。
2. 用户切换语言后保存到浏览器本地，刷新和重新登录仍保持上次选择。
3. 不根据浏览器语言自动切换，避免仓库公共电脑语言发生意外变化。
4. 打印与导出直接跟随当前界面语言，不增加第二套语言选择器。
5. 后端业务校验和异常消息根据请求头 `Accept-Language` 返回相应语言。
6. 翻译资源跟随代码和 Git 版本发布，不新增翻译数据库或外部翻译服务。
7. 缺失翻译以简体中文兜底，同时在开发环境和测试中报告缺失键。

## 3. 当前基础与问题

项目已经安装并接入 `vue-i18n`，已有语言选择组件、语言状态仓库、`Accept-Language` 请求头和中英文基础资源。Ant Design Vue 和 Day.js 也自带四种目标语言的资源。

当前主要问题：

- `enableI18n` 被关闭。
- 初始化逻辑每次启动都会把已保存语言重置成简体中文。
- 现有资源只覆盖少量框架文案。
- 约 622 个前端源码文件包含中文，其中业务页面约 361 个。
- 菜单标题来自数据库，但当前路由直接使用后端中文标题。
- 打印和导出代码中存在独立的 HTML、工作表标题与列名硬编码。
- 后端存在大量中文业务异常和校验消息。

## 4. 总体架构

### 4.1 前端资源

保留 `vue-i18n`，按语言和业务域组织翻译：

```text
src/locales/lang/<locale>/
  common.json
  auth.json
  menu.json
  system.json
  product.json
  order.json
  inbound.json
  outbound.json
  inventory.json
  warehouse.json
  finance.json
  dashboard.json
  print.json
```

四种语言必须拥有相同的键结构。翻译键采用稳定的业务语义，例如 `inbound.receive.confirm`，不得使用中文原文作为键。

### 4.2 动态菜单和路由标题

菜单通过稳定的菜单 `path` 映射到 `menu.<path>` 翻译键。目录、菜单、标签页、页面标题和面包屑均读取同一翻译结果。找不到映射时使用后端返回的原始标题，保证新增菜单不会阻断导航。

菜单翻译不修改数据库结构，避免语言数据与生产数据库迁移耦合。

### 4.3 组件与业务页面

公共按钮、筛选项、分页、空状态、上传、确认框和表单校验优先使用公共翻译键。业务专用文字放入对应业务域资源。

后端返回的稳定状态代码、品质代码、库位类型和订单类型由前端代码映射为翻译键。用户录入或接口返回的业务名称保持原文。

### 4.4 日期、数字和货币

新增统一格式化工具，根据当前语言使用 `Intl.DateTimeFormat`、`Intl.NumberFormat` 和 `Intl.NumberFormat` 的货币模式。金额币种由业务数据决定，语言只改变分隔符、货币符号位置和日期表现，不转换金额或币种。

### 4.5 打印与导出

打印构造器和 Excel 导出函数显式接收当前 `locale` 与翻译函数，禁止在独立窗口模板中继续写死 `zh-CN`。需要覆盖：

- 入库单、商品条码、货物对照表
- 上架记录、拣货单和出库作业辅助内容
- 退货质检、报废、盘点和库位调整
- 财务单据与资金流水
- Excel 文件名、工作表名称、表头、合计和日期

平台原始面单属于外部平台业务文件，不修改其内容；系统在面单外围增加的说明按当前语言翻译。

### 4.6 后端消息

使用 Spring `MessageSource` 管理四套消息资源。业务异常使用稳定消息键及参数，例如：

```java
throw new LocalizedBusinessException("inventory.insufficient", skuCode, availableQty);
```

全局异常处理器根据 Spring 当前 `Locale` 解析消息。请求语言继续通过现有 `Accept-Language` 传递。日志保留消息键、参数及技术异常，便于排查；仅用户可见响应翻译。

## 5. 实施顺序

1. 修复语言初始化、持久化和切换机制，增加乌克兰语、俄语及 UI 组件语言包。
2. 国际化布局、登录、菜单、标签页、公共按钮和通用校验。
3. 按 ERP 货主端、WMS 服务商端、海外仓平台端逐业务域迁移页面。
4. 迁移全部打印和导出代码。
5. 建立后端消息解析基础设施，按业务模块迁移用户可见异常。
6. 执行翻译键一致性检查、中文残留检查、单元测试、类型检查、构建和四语言视觉检查。

每个阶段独立提交，方便审查和回滚；全部阶段完成后才视为四语言功能交付。

## 6. 错误处理与回退

- 不支持或损坏的本地语言值重置为 `zh-CN`。
- 异步语言包加载失败时保持当前语言，并提示切换失败。
- 缺失前端翻译键回退到中文资源。
- 缺失后端消息键回退到中文消息；若中文也不存在，则返回安全的通用错误并在日志记录消息键。
- 语言切换期间不清空用户表单、筛选条件或当前页签。

## 7. 测试与验收

### 7.1 自动化检查

- 四语言 JSON 键集合完全一致。
- 配置中的四种语言均可按需加载。
- 刷新与重新登录保持语言。
- 动态菜单、页面标题和标签页同步切换。
- 后端同一错误在四种 `Accept-Language` 下返回对应消息。
- 关键打印 HTML 和 Excel 的标题、列名随语言变化。
- 扫描用户可见模板、脚本和后端异常中的残留中文；允许注释、日志和测试数据进入白名单。

### 7.2 构建与回归

- 前端类型检查、单元测试和生产构建通过。
- 后端相关模块测试与打包通过。
- 中文模式下原有普通业务流程不发生行为变化。

### 7.3 视觉验收

在桌面与窄屏视口分别检查四种语言，重点处理英文、乌克兰语和俄语的长单词，确保筛选栏、按钮、表格、抽屉、弹窗和打印区域不重叠、不截断。

## 8. 非目标

- 不翻译用户录入和第三方平台返回的业务数据。
- 不进行币种换算。
- 不为不同账号把语言保存到数据库。
- 不提供在线翻译编辑后台。
- 不改变外部电商平台生成的原始面单。
