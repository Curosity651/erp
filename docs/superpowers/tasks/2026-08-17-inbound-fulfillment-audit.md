# 收货、上架、出库与拣货链路审计

## 审计范围

本轮按以下正常业务链路检查：

1. 货主创建并提交入库单。
2. 海外仓扫码收货、上传凭证、确认实收数量。
3. 海外仓按逻辑库位完成上架并生成库存。
4. 货主在订单管理确认发货，创建一单一包裹履约单并预占库存。
5. 海外仓确认下架、生成拣货任务、按库位和内部 SKU 扫描拣货。
6. 获取平台面单、扫描核验、打包并签出。
7. 平台取消、货主取消和库存释放。

任务一与任务二已经完成。本文记录的后续链路问题已于 2026-08-17 修复，并完成后端全量测试、前端构建和运行库迁移。

## P1：海外仓上架无法读取货主 SKU（已修复）

### 现象与原因

- 海外仓平台请求的 `TenantContext` 为 `-1`。
- `sku` 是租户隔离表，普通 `SkuMapper` 查询会自动附加 `tenant_id = -1`。
- `LogicalInboundPutawayService` 和 `LocationRecommendationService` 直接查询 SKU，没有临时切换到入库单的 `erpTenantId`。
- 当前活库的 129 条 SKU 全属于 JHIN（`tenant_id = 6`），所以上架计划会稳定出现“SKU不存在”。

### 修复方案

1. 在上架计划及上架提交中，使用 `TenantContext.runAs(order.getErpTenantId(), ...)` 读取 SKU 主数据。
2. 推荐服务改为接收已按货主读取的 SKU，或确保其内部查询也运行在货主上下文中。
3. 平台上下文只用于 WMS 物理作业数据，不能直接查询租户隔离的 ERP 商品表。
4. 增加“平台操作 JHIN 入库单并读取 JHIN SKU”的集成测试。

## P1：库存预占缺少履约商品与库位关联，拣货任务无法生成（已修复）

### 现象与原因

- `WmsInventoryReservation` 和拣货任务代码要求 `fulfillment_item_id`、`location_id`。
- `InventoryReservationRequest` 没有商品明细 ID。
- `LocationInventoryService.reserve()` 创建预占时只写履约单、库存行和数量，没有写商品明细和库位。
- 活库 `wms_inventory_reservation` 也没有上述字段以及 `released_time`、`shipped_time`。
- `V106` 使用 `CREATE TABLE IF NOT EXISTS`，无法升级已由 `V103` 创建的旧表。

结果是订单可以进入“待下架”，但生成拣货任务时会报“履约商品不存在”或“预占库位不存在”；释放和签出还会因时间字段不存在而执行 SQL 失败。

### 修复方案

1. 新增增量迁移，使用 `ALTER TABLE` 补充四个缺失字段及必要索引。
2. 创建履约商品快照后保留其 ID，并传入库存预占请求。
3. 预占每个库存行时写入 `fulfillment_item_id` 和该库存行的 `location_id`。
4. 人工出库提交复用同一套按履约商品明细预占的接口。
5. 测试一个 SKU 分布在两个库位时，生成两条预占和两条可拣明细，商品 ID 相同、库位 ID 各自正确。

## P1：仓库履约进度没有持续同步到货主订单（已修复）

### 现象与原因

- 首次提交只写 `WAITING_SHELF`。
- 确认下架、创建拣货任务、拣货完成、打包完成均未更新 `erp_order.warehouse_fulfillment_status`。
- 只有取消和最终签出会再次更新 ERP 订单。

因此货主端可能一直显示“待下架”，直到订单最终签出，无法看到待拣货、拣货中、待打包和已打包的真实进度。

### 修复方案

1. 封装统一的履约状态推进服务。
2. WMS 本地状态 CAS 成功后，在同一事务内按来源订单 ID 部分更新 ERP 内部状态。
3. 写回节点包括 `WAITING_PICK`、`PICKING`、`WAITING_PACK`、`PACKED`、`SHIPPED` 和取消状态。
4. ERP 内部状态只表示仓库作业进度，平台实际状态仍由平台 API 同步结果负责。
5. 前端确认发货条件同时检查内部履约状态，防止活动履约单被重复提交。

## P1：拣货后平台取消会被旧状态覆盖（已修复）

### 现象与原因

`FulfillmentStatusSyncService.platformCancelled()` 先把 WMS 状态 CAS 为 `CANCEL_RETURNING`，随后用此前读取的完整旧实体更新取消原因。该旧实体仍携带原状态，`updateById` 会把状态覆盖回 `PICKING`、`WAITING_PACK` 或 `PACKED`。

### 修复方案

1. 不再用完整旧实体更新取消原因。
2. 使用只更新 `cancel_reason` 的部分实体，或在同一条 CAS SQL 中同时写状态与原因。
3. ERP 状态写回必须以 WMS 状态更新成功为前提。
4. 增加待拣货后、拣货中、待打包、已打包四种取消测试。

## P1：面单核验使用平台订单号代替真实面单条码（已修复）

### 现象与原因

- 新履约链路的 `PlatformAdapterSupport` 不论 Ozon、WB 还是 Yandex，都把 `sourceOrderNo` 当成 `labelBarcode`。
- 原面单链路已经保存平台返回的 `labelVerifyCodes`，WB 还明确包含 sticker barcode、partA+partB。
- 扫描真实 WB 面单时，条码通常不会等于 ERP 保存的平台订单号，因此正常核验可能失败。

### 修复方案

1. 新履约链路复用已有 `labelVerifyCodes` 校验规则。
2. 允许的平台核验码包括平台订单号、shipmentId 及平台返回的全部面单条码。
3. `PlatformLabelResult` 可保留展示用主码，但后端核验必须按允许码集合判断。
4. 为 Ozon、WB、Yandex 分别增加真实返回模型的条码测试。

## P1：上架接口未校验目标库位属于入库单仓库（已修复）

### 现象与原因

- 上架提交按库位 ID 加锁后，把查到的库位直接放入当前仓库的库位映射。
- 没有再次校验 `location.warehouseId == order.warehouseId`。
- 经过修改请求或过期页面可把库存记录写成“仓库 A + 仓库 B 的库位 ID”，形成无法解释的库存归属。

### 修复方案

1. 增加按 `locationId + warehouseId` 加锁查询，或加锁后强制比较仓库 ID。
2. 同时校验分区属于同一仓库。
3. 增加跨仓库目标库位提交必须回滚的测试。

## P2：公共暂存区判断使用了错误字段（已修复）

### 现象与原因

- 新库位模型中，暂存区由 `wms_zone.zone_type = TEMP` 表示。
- `location_type` 是标准、大件、小件等库位类型。
- 当前 `isPublicTemp()` 却判断 `location.locationType == TEMP`，导致“TEMP 分区 + STANDARD 库位类型 + 公共共享”的正常库位不被识别为公共暂存区。

### 修复方案

1. 统一按 `zone_type = TEMP && public_shared = 1` 判断公共暂存区。
2. 上架计划和上架提交共用同一个判断函数。
3. 增加公共暂存区无需专属货架分配即可上架的测试。

## P2：取消后的订单再次确认会形成 ERP/WMS 状态矛盾（已修复）

### 现象与原因

- `createAndReserve()` 按来源订单查到任何历史履约单后直接返回其 ID。
- 如果历史单已取消，不会重新预占，也不会把 WMS 状态重新推进。
- 提交服务仍会把 ERP 内部状态写成 `WAITING_SHELF`。

### 修复方案

1. 活动履约单重复提交返回幂等成功，但不能重复预占。
2. 已取消订单若允许重新提交，提供显式“重新提交”逻辑：重新预占并以 CAS 推进到 `WAITING_SHELF`。
3. 若业务决定不允许重新提交，则后端明确拒绝，前端隐藏确认按钮。
4. 不允许仅修改 ERP 状态而不修改 WMS 履约单与预占。

## 建议实施顺序

1. 先修复预占表迁移和商品/库位关联，否则出库拣货主链路无法运行。
2. 修复平台上下文读取货主 SKU，否则收货后的上架主链路无法运行。
3. 修复 WMS 与 ERP 状态同步及取消覆盖问题。
4. 修复平台面单真实条码核验。
5. 补上跨仓库库位校验、公共暂存区判断和取消后重提策略。
6. 使用真实 JHIN SKU 做一次完整回归：收货凭证 → 上架 → 库存预占 → 下架 → 拣货扫描 → 面单核验 → 打包 → 签出 → 库存扣减与计费。

## 实施结果

- 上架读取 SKU 时按入库单货主切换租户上下文，并校验目标库位和分区属于入库仓库。
- 库存预占完整记录履约明细和逻辑库位，运行库已补齐关联字段、时间字段和查询索引。
- 履约状态在待拣货、拣货中、待打包、已打包、已签出和取消节点同步到 ERP 订单。
- 平台取消使用状态与原因原子更新，不再被旧实体覆盖。
- 面单核验复用平台订单保存的订单号、shipmentId 和真实条码集合。
- 公共暂存区统一按 `zone_type = TEMP && public_shared = 1` 判断。
- 已取消履约单明确禁止再次提交，前后端规则保持一致。
- 后端全量测试 `189/189` 通过；前端类型检查和生产构建通过。
